# The category-value catalogue

A category record states its value as a name:

```xml
<Record type="HKCategoryTypeIdentifierLowerBackPain" value="HKCategoryValueSeverityModerate" …/>
```

The export's DTD declares that attribute as `value CDATA #IMPLIED` and can do
no better, because which names are legal depends on the record's type: a
severity for a symptom, a stage for sleep, `HKCategoryValueNotApplicable` for a
mindful session. The export never says which. Apple's HealthKit documentation
does, per identifier, and `category_values.json` is that mapping, generated by
[`tools/refresh_catalog.py`](../../tools/refresh_catalog.py).

## What this is not

**It is not a second schema.** `applehealth/schema/` stays the source of truth
for what an export contains — elements, attributes, nesting. The catalogue only
attaches meaning to values an export already carries, and it is deliberately
powerless:

* Nothing on the import path reads it. Imports do not touch it at all; it is
  loaded by `derive`, into two tables the views join against.
* `records.value_text` keeps the raw name. The translation is added beside it,
  never in place of it.
* Every join is an outer one with a fallback to the raw name. A type or value
  the catalogue has never heard of — and Apple adds both with every iOS
  release — comes through unchanged rather than empty.

So the catalogue going stale costs you a column, not a record. That is the
opposite trade from the DTD, where being wrong means data lands in `unhandled`
and gets reported.

## Where the data comes from

The documentation pages are rendered client-side and yield nothing to a plain
fetch, but the JSON behind them is served under a parallel URL:

| Page | JSON |
| --- | --- |
| `developer.apple.com/documentation/healthkit/hkcategorytypeidentifier` | `…/tutorials/data/documentation/healthkit/hkcategorytypeidentifier.json` |
| `…/documentation/healthkit/symptom-type-identifiers` | `…/tutorials/data/documentation/healthkit/symptom-type-identifiers.json` |

Three fields carry the load:

* **`metadata.externalID`** — `c:@HKCategoryTypeIdentifierBloating`. This is the
  Objective-C name, which is exactly the spelling the XML uses. The Swift name
  on the same page is `bloating`; deriving the export spelling from it would be
  a guess, and this is the fact.
* **the `HKCategoryValue…` link in a type's discussion** — how the docs say
  which enumeration a type's values come from. Some pages link the enumeration
  (`HKCategoryValueSeverity`), others one of its members
  (`HKCategoryValue.notApplicable`); both name it.
* **`topicSections`** — Apple's own grouping, which becomes `family` and
  `topic`.

## Fields, and which of them are Apple's

Everything in the generated file is read from the documentation, with one
exception, marked below.

| Field | Where it comes from |
| --- | --- |
| `types.<id>.enum` | the value-enumeration link on the type's page |
| `types.<id>.family` | the index section: Symptoms, Reproductive Health, … |
| `types.<id>.topic` | the finer section on the symptom page: Musculoskeletal, … |
| `enums.<e>.members[].name` | enumeration name + case name, per the ObjC symbol |
| `enums.<e>.members[].short` | the same, minus the enumeration prefix |
| `enums.<e>.scale` | **a judgement — see below** |
| `enums.<e>.members[].ordinal` | position on that ladder, for scales only |

**`scale` is the one judgement call.** Apple lists an enumeration's members in
an order but never says the order means anything, so the generator carries a
short explicit list of the enumerations whose members really are a ladder
(`SCALE_ENUMS`) rather than inferring it. The order is not always one:
`HKCategoryValueVaginalBleeding` reads Unspecified, Light, Medium, Heavy,
*None* — inferring from that would rank `None` above `Heavy`. Members that sit
beside a ladder rather than on it (`Unspecified`) get no ordinal even in a
scale.

An `ordinal` is for sorting and plotting. It is not a measurement: the distance
from Mild to Moderate is not a quantity, and averaging a column of them means
nothing.

## Refreshing it

```bash
poe refresh-catalog
```

About a hundred requests, a couple of minutes, and the result is committed.
Review the diff as documentation moving rather than code changing. `--dry-run`
prints the counts without writing.

The generator fails loudly if the pages stop looking the way it expects, rather
than writing a half-filled catalogue — a missing entry would otherwise show up
months later as a column of raw `HKCategoryValue…` names.

## What is deliberately not here

* **Apple's prose.** The descriptions on those pages are theirs; identifier
  names, enumeration membership and grouping are facts, and only those are
  copied.
* **Quantity types.** The same documentation states, per quantity identifier,
  whether its samples are cumulative or discrete — which is what would tell
  `daily_metrics` whether `total` or `mean` is the meaningful column, instead
  of leaving the reader to know. That is a second, larger change, and it is not
  in this file yet.
* **Types Apple does not document a value enumeration for.** One at the time of
  writing: `HKCategoryTypeIdentifierHypertensionEvent`. It gets no translation,
  which is the same thing that happens to anything new.
